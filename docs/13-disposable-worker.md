# Disposable tool worker and approval boundary

## Result

`tentaflake.worker.agents.<container>` creates a per-controller host queue for
untrusted shell, build, and foreign-code jobs. The controller writes only a
small JSON request. A host-side Rust orchestrator captures the request into
private state, takes a bounded workspace snapshot, and creates a short-lived
OCI container with `runsc`, `network=none`, numeric non-root user,
`cap-drop=ALL`, `no-new-privileges`, read-only root, bounded tmpfs, and
CPU/RAM/swap/PID/runtime limits. Docker workers explicitly select
`docker-default` AppArmor; Docker/Podman retain their default seccomp policy
and unconfined overrides are never exposed through the request. The worker
receives no agent, provider, Git, backup, or infrastructure credential.

The worker is a second containment boundary. It does not make the controller,
OCI daemon, kernel, gVisor, worker toolchain, or submitted code trustworthy.
It is optional for a deliberately stopped scaffold, but an automatically
started balanced controller fails evaluation without its matching worker.

## Enable one worker

The key must exactly match the OCI container generated by the builder. The
workspace and numeric UID/GID must also match; evaluation fails otherwise.

```nix
tentaflake.worker.agents.hermes-coding = {
  enable = true;
  workspace =
    "/var/lib/hermes-coding/workspace";
  containerUid = 10000;
  containerGid = 10000;

  maxSnapshotBytes = 1024 * 1024 * 1024;
  maxSnapshotEntries = 200000;
  maxTimeoutSeconds = 900;
  memory = "2g";
  memorySwap = "2g";
  cpus = "2.0";
  pidsLimit = 512;
  workspaceTmpfsSize = "2g";
  tmpTmpfsSize = "256m";
};
```

ZeroClaw uses `/var/lib/zeroclaw-<name>/data` with UID/GID 65534.

The host service runs with a real group-database entry matching the numeric
container GID. Tentaflake creates one deterministic `tfw-gid-<gid>` group per
non-nogroup GID and reuses `nogroup` for GID 65534. If a deployment already
owns a custom container GID, set `hostGroup` to that existing group; its
explicit host GID must match or evaluation fails.

The default image is built by Nix from the pinned nixpkgs input. It contains an
offline Rust/C/build toolchain. `CARGO_NET_OFFLINE=true` is set, and the
worker has no network namespace route regardless of tool configuration. A
deployment may replace `worker.image`; its default reference follows the
image's `imageName` and `imageTag`. Set `worker.imageReference` explicitly for
images without that metadata. The module loads the Nix derivation locally
without pulling the reference from a registry.

## Submit a job

Write one complete file atomically when practical:

```json
{
  "version": 1,
  "id": "cargo_test_1",
  "action_class": "local-reversible",
  "argv": ["cargo", "test", "--offline"],
  "timeout_seconds": 300
}
```

The path is:

```text
<workspace>/.tentaflake-worker/inbox/
  cargo_test_1.json
```

IDs are bounded lowercase ASCII identifiers. The parser rejects unknown
fields, oversized requests, empty or oversized argument lists, NUL bytes,
unsupported versions, duplicate IDs, and timeouts above policy.

The snapshot walker opens the configured workspace through Linux `openat2`
with `RESOLVE_NO_MAGICLINKS | RESOLVE_NO_SYMLINKS`. On kernels or filtered VM
environments that return `ENOSYS`, it falls back to descriptor-relative,
component-by-component `openat` calls with `O_DIRECTORY | O_NOFOLLOW` and
rejects relative paths plus dot or parent components.
It then traverses by directory/file descriptors, does not follow file
symlinks, excludes the queue directory, rejects special files, and stops at
byte and entry ceilings. Directory enumeration retains at most the remaining
entry budget and rejects the first excess entry before sorting or copying that
directory; the top-level queue directory does not consume this budget.
This prevents an agent-controlled top-level symlink
or rename race from turning the root worker into a reader of an unrelated host
path. The private host snapshot stays root-owned, while the source owner's read
and execute bits are mirrored to the already-declared capsule GID before the
read-only bind mount. Private workspace entries therefore remain readable
without granting the host worker `CAP_CHOWN`. Inside the capsule, the job user
recreates the snapshot without preserving host ownership metadata as
additional authority.

## Action classes and approval

| Class | Behavior |
|---|---|
| `local-reversible` | runs automatically in the offline disposable capsule |
| `external-reversible` | requires host approval |
| `irreversible` | requires host approval |
| `financial` | requires host approval |
| `production` | requires host approval |
| `communicative` | requires host approval |
| `privileged` | requires host approval, but gains no extra worker authority |
| `forbidden` | always rejected |

The host captures a validated request below
`/var/lib/tentaflake-worker-<container>/pending/` before approval. The agent
cannot mutate that private copy. Approve or deny the exact ID from an operator
session:

```text
sudo tentaflake-worker --config \
  /etc/tentaflake/workers/hermes-coding.json \
  approve message_1

sudo tentaflake-worker --config \
  /etc/tentaflake/workers/hermes-coding.json \
  deny message_1
```

The root operator command adopts the worker's declared capsule group before it
creates a snapshot. Direct approval therefore uses the same read-only snapshot
permissions as the systemd queue service and does not require `CAP_CHOWN`.

For an operator interface, use the separate JSON commands:

```text
sudo tentaflake-worker --config \
  /etc/tentaflake/workers/hermes-coding.json requests

sudo tentaflake-worker --config \
  /etc/tentaflake/workers/hermes-coding.json \
  decide message_1 approve --expected-digest <request_digest>

sudo tentaflake-worker --config \
  /etc/tentaflake/workers/hermes-coding.json \
  decide message_1 deny --expected-digest <request_digest>
```

`requests` reads captured private pending state, never the controller's inbox.
It returns `schema_version`, `agent`, `initialized`, `truncated`, and `requests`.
Each row carries the exact `id`, full `argv` array, `action_class`,
`timeout_seconds`, fixed capsule `cwd` (`/workspace`), `request_digest`,
`state` (`pending`), `approval_status`, `can_approve`, and `can_deny`.
The digest is lowercase SHA-256 of the complete validated request serialized
by the worker, including version, ID, action class, all arguments, and the
effective timeout. Display every argument with its boundaries before confirming
a decision. Arguments are untrusted content and can contain sensitive data;
they are not instructions to the interface and should not enter request logs.

These commands acquire the existing private lock without waiting. They neither
initialize the queue nor adopt the capsule group, touch the workspace, recover
jobs, or invoke the container runtime. An uninitialized queue lists no requests;
a busy worker returns `busy:` promptly, including while a long job is executing.
Inspection uses read-only file descriptors and works with read-only worker
state. Only `decide` requires write access to private worker state for the
decision receipt and drain wakeup.

Inspection permits at most 256 pending directory entries and 8 MiB of entry
sizes, or the configured queue limits when smaller. Each request is limited to
64 KiB, or the configured request limit when smaller. Responses include at most
100 complete rows and 256 KiB of JSON. `truncated: true` means more rows remain;
no returned argument is shortened. Process the displayed requests and refresh
to inspect the remainder. Unsafe links, ownership/permissions, malformed state,
or scan overflow fail closed instead of producing partial approval evidence.

`decide` records authorization only. It returns a durable receipt containing
`schema_version`, `agent`, `job_id`, `request_digest`, `decision`,
`state: "recorded"`, and `drain_required: true`. It does not execute the job or
write a terminal job result. Before publishing a new decision, it durably
publishes a private `.drain-request` marker under the same queue lock. The
per-agent path unit watches this marker as well as the inbox and rechecks it
when the worker exits. Thus a decision recorded after a drain releases its lock
but before systemd finishes that invocation still triggers another drain.
Only a new drain consumes the marker, at entry under the lock. An interrupted
publication may cause a harmless extra drain, not a lost committed decision.
An operator interface may additionally start the normal per-agent worker
service for prompt scheduling; it must not restart or kill a running worker.
The next drain runs an approved request or finalizes a denied request without OCI.
The existing `approve` command still processes ready work immediately, and the
existing `deny` command still finalizes a denial directly.

The first recorded decision wins. Repeating the same decision and digest
returns the same receipt, including after the request has retired. A different
decision, changed request, existing legacy approval, or terminal/running job
conflicts. `forbidden` and automatic `local-reversible` requests cannot be
approved. A stale decision also prevents drain from dispatching a replacement
request with the same ID. Publication or acknowledgement failures return
`uncertain:`: the decision may already be durable, so preserve the identity and
retry that exact decision rather than inventing a new request or assuming it
was rejected.

Private `decisions/<id>` receipts survive result expiration and prevent job-ID
reuse. Their separate limit is 4096 records / 4 MiB. At capacity, existing
decisions remain retryable but new decisions fail visibly. Archive or retire
decision history only through an explicit offline operator procedure, with
all writers stopped and with the loss of replay protection understood.

Approval is an authorization decision outside the LLM. It does not change the
capsule: approved jobs still have no network, secrets, host devices, runtime
socket, added capabilities, or writable host bind. Therefore an approved
`communicative` or `financial` job cannot itself perform that external action.
Such effects require a separate narrow broker; no generic external-side-effect
broker is implemented yet.

## Results and cleanup

The worker captures bounded runtime logs and exit status. Docker capsules use
the `local` driver with a one-file size cap and compression disabled; Podman
capsules use bounded `k8s-file` logging. The worker separately caps the
published `job.log`. A job may place files below `artifacts/` in its tmpfs
workspace. After the job command returns, the capsule wrapper records its real
exit status and keeps the container alive briefly. The worker streams a tar
archive through `docker exec` or `podman exec` from inside the `runsc` mount
namespace while the bounded tmpfs is still mounted. Its host importer enforces
the snapshot byte and entry ceilings, accepts only relative regular files and
directories, rejects links and special files, and normalizes result
permissions. The worker rechecks the completion marker to exclude a concurrent
handoff and only then signals the wrapper to exit. The import lands in the
worker's private result directory and is exposed read-only to the controller:

```text
/run/tentaflake-worker/results/<id>/
  result.json
  job.log
  artifacts/
```

The controller chooses whether to copy a reviewed artifact into its persistent
workspace. The worker never writes an artifact directly back into that
workspace, and the capsule receives no writable host bind for this handoff.
Results retain their existing 14-day tmpfiles policy; capacity admission never
deletes results to make room. Empty private ID receipts survive result expiry
to prevent replay. The prompt-free JSONL audit rotates daily with 14 generations;
each active file has a 1 MiB hard append ceiling. Repeated failed admissions
cannot grow it indefinitely; a full audit fails closed until rotation or
explicit operator archival.

## Queue ownership, capacity and recovery

Worker drains and operator approval/denial commands hold one per-agent private
file lock. A competing command fails visibly with a busy diagnostic; it does
not modify approvals or start a second execution. Requests and approvals are
written to private staging files, synced, then published atomically without
replacing an existing record. The inbox can live on a separate quota filesystem;
capture therefore copies into private state before removing the inbox entry.

| Durable state | Transition and restart behavior |
|---|---|
| `pending/<id>.json` | Validated immutable request; approval remains outside the agent. |
| `running/<id>.json` | Atomically claimed and synced before any OCI dispatch. |
| `decisions/<id>` | Digest-bound operator decision retained after retirement; an exact retry never changes it. |
| `results/<id>/result.json` | Terminal result and artifacts synced before publication. |
| `reservations/<id>` | Empty durable no-replay receipt; retained independently of result capacity. |

After a crash, a running claim is never dispatched again. Recovery checks the
exact container name and ownership label before removing its disposable
container and private staging. If no terminal result exists, it publishes
`interrupted`: the execution outcome is unknown. Review it before submitting a
new ID. A completed result with a stale private request is retained and the
request retired without replay. Runtime listing/ownership errors preserve the
claim and fail closed. This is conservative crash recovery, not a promise of
exactly-once effects across operator rollback or deleted state.

`maxInboxEntries` and `maxInboxBytes` default to 256 entries and 8 MiB;
`maxQueueEntries` and `maxQueueBytes` apply the same defaults jointly to private
pending and running requests. Inbox scans count ignored names and staging files
before allocating an unbounded list. Summed entry sizes include links and
directories, but do not traverse directory trees; the workspace quota bounds
those trees. Admission rejects overflow visibly, records `queue-overload`, and
preserves the unaccepted inbox request. Existing ready jobs drain before new
admission, so an overflowing inbox cannot prevent completed work from retiring.
Retained storage is separately admitted under the same lock. The positive
options `maxRetainedResultBytes`, `maxRetainedResults` and `maxRetainedEntries`
default to **4 GiB**, **1024 jobs** and **1,000,000 tree entries**, respectively.
Their JSON names are `max_retained_result_bytes`, `max_retained_results` and
`max_retained_entries`; old JSON configurations use the same finite defaults.
Completed trees consume their actual payload bytes and entries. Before a
claim or terminal rejection, admission reserves a full worst-case job:
`2 * maxSnapshotBytes + maxLogBytes + 16 KiB` and
`2 * maxSnapshotEntries + 8` entries. These cover simultaneous input/export,
bounded logs and result metadata. Configurations must fit at least one such
reservation. Running claims retain the full reservation after a crash until
recovery publishes a result and retires the claim; jobs are never replayed.

At capacity, the next request stays pending before OCI dispatch, with no
automatic removal of artifacts or receipts. Existing result expiry or explicit
operator archival releases actual storage capacity. Empty no-replay ID receipts
remain separately bounded at 4096 entries, independent of artifact capacity;
new IDs fail closed at that ceiling just as decision receipts do. Reconcile
receipt history only offline with all writers stopped and the loss of replay
protection understood.

Descriptor-relative scans bound bytes, entries and depth, including interrupted
staging. Unreserved legacy state, unsafe links, special files, hardlinks and
oversized restored trees fail closed without deleting evidence. Artifact imports
count implicit parent directories, not just archive headers. Snapshot copying
and artifact import permit at most 128 nested directories below their tree
root; retained scans additionally allow the `input`, `artifacts-export` or
`artifacts` wrapper, so accepted trees remain recoverable after publication
or a crash. Deeper input is rejected before OCI dispatch. These payload
limits do not claim exact physical disk quotas: filesystem block rounding,
directory/inode overhead and bounded snapshot symlink targets require additional
headroom. Requests, decisions and rotated audits retain separate finite ceilings.

Existing configurations without the new JSON fields use these defaults.
Upgrade with the worker and watcher stopped and preserve a quota-aware backup.
Complete legacy pending records and exact approvals remain valid. Existing
results, running claims or snapshots without reservation receipts now require
explicit offline operator reconciliation: inventory and validate their bounds,
then provision root-owned empty private `reservations/<id>` receipts within
the receipt limit, preserving every job ID and terminal receipt.
Unknown legacy execution must never be resubmitted automatically. Unpublished
private `.new` files are discarded during ordinary queue recovery. Reservation
publication recovery removes only empty, private `.id.new` files with either
one link before publication or exactly two links to the matching published
receipt; the published receipt is preserved. Unknown or unsafe reservation
staging fails closed. Private snapshot descendants may retain source write
bits only behind a verified root-owned, owner-only job directory; these bits
do not prevent interrupted-job recovery or relax published-result permissions.
Malformed legacy pending records fail closed and
preserve a complete inbox copy; inspect the exact job and restore or quarantine
its private record offline before restarting. If restored queues exceed the new
ceilings, explicitly adjust the ceilings or review and reduce the queue offline.
Review pending/running requests before activating a restored backup: a rollback
can predate work that already executed. No existing image is reformatted and
quota-aware backup sources are unchanged.

The path-activated queue service has a ten-second failure-restart delay but no
aggregate systemd start counter. systemd counts successful oneshot activations
against that counter as well, which would otherwise disable a healthy queue
after a small number of ordinary jobs. Per-request resource, timeout, snapshot,
and workspace ceilings remain enforced independently.

Tmpfiles establishes the result root as `02750`; the orchestrator preserves
that inherited setgid bit without trying to reapply it inside the hardened
systemd unit. Published result files therefore retain the controller's exact
numeric group while `RestrictSUIDSGID=true` remains enforced.

The OCI container and temporary host snapshot are removed after every normal
completion, failure, or timeout. A stale container is removed only when its
Tentaflake ownership label exactly matches the configured agent.

Both completion-marker reads (initial polling and post-export validation) share
the job deadline. Their host-side capture is nonblocking and capped at 96 bytes;
a FIFO or stalled exec helper cannot indefinitely retain the queue lock in this
poll. At expiry the local exec process group is killed and reaped, the job is
timed out, and no staged artifacts are published. Container removal still goes
through the existing cleanup guard. This bounds marker polling, not every OCI
control operation or artifact archive stream; those still rely on a responsive
host runtime.

## Verification boundary and remaining risks

Unit tests cover parser/action policy, bounded reads and snapshots, symlink
rejection, control-directory exclusion, and log truncation. Synthetic executable
fixtures cover FIFO-blocked initial and post-export marker polls, timeout
results, cleanup, queue-lock release, and no replay without requiring OCI.
These fixtures do not establish live container-runtime behavior. Module-evaluation
tests cover builder matching and fail-closed configuration. The NixOS VM test
submits real local, approval-required, and forbidden jobs, checks no network or
runtime socket, validates the numeric user and artifacts, and proves container
and snapshot cleanup. That runtime test uses Docker; Podman evaluation is not
live Podman/AppArmor proof.

A derivation evaluation is not proof that Docker/Podman, `runsc`, systemd path
units, tmpfs ceilings, or cleanup worked on an activated host. Run the VM check
and then a deployment-specific live drill before relying on it. The module
also cannot transparently intercept every runtime's built-in terminal tool;
configure the agent/tool policy to submit untrusted execution to this queue.
The posture doctor reports `TFSEC-020` when a secure-profile controller has no
worker, but it cannot prove that every model-selected command used it.
